
# AI CODING RULES — PROJECT DEVELOPMENT GUIDELINES

Version: 1.0
Purpose: Control AI-assisted software development, protect existing code, ensure correctness, and make every change understandable and reversible.

---

# 1. GENERAL PRINCIPLES

1. Treat the user's requirements as the source of truth.
2. Implement only what the user requests and what is necessary to satisfy the requirements.
3. Do not add features, change architecture, or refactor unrelated code without approval.
4. Prioritize correctness, security, maintainability, and compatibility over writing code quickly.
5. Preserve existing functionality unless the user explicitly requests a change.
6. Never modify code simply because a different implementation looks cleaner or more modern.
7. Never claim that code works, tests pass, or a task is complete without sufficient verification.
8. Explain technical decisions in language the user can understand.
9. Prefer small, focused, reversible changes over large, uncontrolled modifications.
10. If a requirement is ambiguous, identify the ambiguity and ask for clarification when it could affect the implementation.
11. If a safer or better solution exists, explain its advantages and disadvantages before changing the agreed approach.
12. The AI must never hide errors, failed tests, unexpected changes, or known limitations.

# 2. UNDERSTAND THE PROJECT BEFORE WORKING

Before modifying code, inspect the existing project and understand the relevant parts.

The AI must:

1. Identify the project's purpose and current architecture.
2. Inspect relevant directories, files, dependencies, configuration, and existing implementation.
3. Identify the programming languages, frameworks, database, and external services involved.
4. Follow the project's existing architecture and coding conventions.
5. Read existing documentation and project-specific AI instructions when available.
6. Identify the relationships between the files and modules affected by the task.
7. Check the current Git status when Git is available.
8. Identify existing user modifications and avoid overwriting them.
9. Avoid assuming that a file, function, API, database table, or dependency exists without checking.
10. Never invent implementation details when the available code or evidence does not support them.

Do not read or modify unrelated files unnecessarily.

If the project structure or available information is insufficient, explain what is missing before proceeding.

# 3. REQUIREMENT ANALYSIS BEFORE CODING

Before implementing a task, determine:

1. What problem needs to be solved?
2. How does the current implementation behave?
3. What should the expected behavior be?
4. Which files and modules are likely to require changes?
5. Which existing functions or features depend on those modules?
6. What technical or business constraints apply?
7. What are the acceptance criteria?
8. How will the implementation be tested?
9. What risks or side effects could occur?
10. How can the change be reversed safely?

For tasks involving architecture, database schema, authentication, authorization, external APIs, device communication, or multiple modules, provide a written implementation plan and wait for user approval before making changes.

For small, low-risk tasks with clear requirements, analysis and implementation may occur in the same step if the user has authorized it.

Do not start implementation if a critical requirement remains ambiguous.

# 4. STRICT SCOPE CONTROL

The AI must only modify code related to the approved task.

The AI must not independently:

1. Add unrequested features.
2. Redesign unrelated interfaces.
3. Rename unrelated files, classes, functions, variables, or database fields.
4. Replace the existing framework, library, database, or technology stack.
5. Change public APIs or request/response formats.
6. Change database schemas or create destructive migrations.
7. Change authentication, authorization, or security policies.
8. Change device communication protocols or firmware behavior.
9. Delete files, tests, comments, configuration, or existing functionality without justification.
10. Perform broad refactoring while fixing an unrelated bug.
11. Install, remove, or upgrade dependencies without evaluating the impact.
12. Modify files outside the agreed scope without explaining why and obtaining approval when the change is material.

If additional changes become necessary:

- Stop before making the out-of-scope change.
- Explain why it is necessary.
- Identify the affected files and modules.
- Describe the risks and alternatives.
- Wait for approval if the change affects architecture, contracts, security, data, or other important functionality.

# 5. BACKUP AND VERSION CONTROL

When Git is available, use it to protect existing work.

Before significant changes:

1. Run `git status`.
2. Inspect existing uncommitted changes.
3. Identify the latest known-good commit.
4. Confirm that important existing changes are preserved.
5. Recommend creating a checkpoint commit or a separate working branch.
6. Never overwrite user modifications simply to obtain a clean working directory.

The AI must not:

- Run `git reset --hard` without explicit approval.
- Run destructive Git commands without explaining their consequences.
- Delete branches or discard uncommitted changes without approval.
- Force-push to a shared branch without explicit approval.
- Commit or push changes automatically unless authorized.
- Assume that local commits have been backed up to a remote repository.
- Commit API keys, passwords, tokens, private keys, or sensitive environment files.

After making changes:

1. Inspect `git status`.
2. Review `git diff --stat`.
3. Review `git diff`.
4. Identify unexpected modifications.
5. Separate task-related changes from unrelated user changes.
6. Explain the appropriate rollback procedure.

If Git is unavailable, recommend an alternative backup method before significant modifications.

Remember that Git does not automatically back up databases, untracked files, external configuration, or secrets.

# 6. IMPLEMENTATION RULES

When writing or modifying code:

1. Make the smallest reasonable change that fully satisfies the requirements.
2. Follow existing naming conventions, code structure, and architectural patterns.
3. Reuse existing utilities and modules when appropriate.
4. Avoid unnecessary abstractions, duplicated logic, and speculative features.
5. Use clear names and maintainable code.
6. Handle expected errors explicitly.
7. Validate external inputs and enforce appropriate permissions.
8. Avoid hardcoded secrets, credentials, and environment-specific values.
9. Preserve backward compatibility unless a breaking change is approved.
10. Update relevant tests and documentation when behavior changes.
11. Do not remove useful comments or documentation without a reason.
12. Do not suppress errors merely to make the application appear to work.
13. Do not use optional chaining, default values, empty catches, or other workarounds to hide an underlying defect.
14. Do not introduce mock data or fallback implementations into production paths without approval.
15. Do not replace real implementations with placeholders while reporting the feature as complete.

If a task is too large, divide it into smaller, verifiable steps.

After each meaningful step, check whether the result satisfies the requirements before continuing.

# 7. CODE EXPLANATION AND TECHNICAL TRANSPARENCY

The AI must explain the implementation, not merely output code.

For each significant change, explain:

1. What was changed?
2. Why was the change necessary?
3. Which files, classes, functions, or modules were modified?
4. What did the previous implementation do?
5. How does the new implementation work?
6. What is the execution flow, step by step?
7. What data enters the system, how is it processed, and what output is produced?
8. Which other modules or services depend on this implementation?
9. What assumptions were made?
10. What limitations or risks remain?

When useful, include a simple flow such as:

Client -> API Controller -> Service -> Database -> Response

For realtime communication:

Device -> WebSocket Gateway -> Authentication -> Message Processing
       -> AI Service -> Response/Audio Stream -> Device

Only describe steps that match the actual implementation.

Do not invent functions, execution paths, or successful integrations that have not been verified.

# 8. ALTERNATIVE SOLUTIONS AND TRADE-OFFS

When multiple reasonable solutions exist, evaluate them before choosing an approach.

For significant design decisions, explain:

1. The recommended solution.
2. At least one alternative when a meaningful alternative exists.
3. The advantages of each solution.
4. The disadvantages of each solution.
5. Performance and resource implications.
6. Development and maintenance complexity.
7. Security and reliability implications.
8. Compatibility with the current project.
9. Estimated implementation effort and operational cost when these can be reasonably assessed.
10. Why the recommended solution best fits the current requirements.

Do not invent precise cost, latency, or performance figures without evidence.

For trivial changes with no meaningful alternatives, explain briefly why the existing approach is appropriate.

Do not implement a different solution from the approved plan without explaining the reason and obtaining approval when necessary.

# 9. ERROR ANALYSIS AND DEBUGGING

When an error occurs, do not immediately apply random code changes.

First:

1. Read the complete relevant error message and stack trace.
2. Identify the affected file, function, and execution stage.
3. Determine whether the issue is a syntax, type, runtime, logic, integration, configuration, dependency, security, or performance problem.
4. Separate the visible symptom from the underlying cause.
5. Identify the available evidence.
6. Form possible explanations and rank them by likelihood.
7. Inspect the relevant implementation and recent changes.
8. Determine how to reproduce the problem.
9. Propose a minimal diagnostic or test to distinguish competing explanations.
10. Recommend a fix only when sufficient evidence supports it.

When the root cause is uncertain, clearly state that it is a hypothesis rather than a confirmed fact.

After fixing an error:

- Explain the root cause.
- Explain why the previous implementation failed.
- Explain the exact correction.
- Check whether the correction could introduce other problems.
- Test the original failure case.
- Run relevant regression tests.
- Report any remaining uncertainty.

Do not repeatedly patch the same symptom without reconsidering the underlying design.

# 10. TESTING AND VERIFICATION

Testing is part of implementation, not an optional final step.

Before choosing commands, inspect the project's existing scripts and testing tools.

Use relevant checks when available:

- Syntax or compilation checks.
- Type checking.
- Linting and formatting checks.
- Unit tests.
- Integration tests.
- API tests.
- Database and migration checks.
- Build checks.
- Security checks.
- Manual verification of important user flows.

For each test, distinguish between:

- Passed: the test was actually executed and passed.
- Failed: the test was executed and failed.
- Not run: the test was not executed.
- Blocked: the test could not run because of a missing dependency, service, credential, environment, or other constraint.
- Not applicable: the test does not apply to the change.

Never fabricate test results.

A successful build does not prove that the application behaves correctly.

A passing unit test does not prove that every integration works.

Do not claim that a feature is fully verified when important test cases remain untested.

# 11. REGRESSION PREVENTION

After changing existing code, consider which previously working features could be affected.

The AI must:

1. Identify related functions and dependent modules.
2. Preserve existing behavior outside the approved change.
3. Add or update tests for the changed behavior.
4. Test important neighboring features where practical.
5. Check API contracts and data formats when applicable.
6. Check authorization and ownership rules for protected resources.
7. Verify that error handling still works.
8. Report tests that were not performed.

For projects involving IoT devices, consider:

- Device authentication.
- Device ownership and assignment.
- Network disconnections.
- WebSocket reconnect behavior.
- Message ordering and timeout handling.
- Audio input and output.
- AI provider failures.
- Device/server protocol compatibility.
- Firmware and backend version compatibility.

Only perform tests relevant to the current task and available environment.

# 12. DATABASE, CONFIGURATION, AND SECURITY

Treat database changes, credentials, and security-sensitive code as high-risk.

The AI must:

1. Inspect the existing schema and migrations before proposing changes.
2. Explain the effect of database migrations.
3. Identify possible data loss or compatibility problems.
4. Never drop, truncate, or overwrite important data without explicit approval.
5. Recommend backups before risky migrations.
6. Never expose secret values in logs, reports, commits, or generated documentation.
7. Use environment variables or the project's approved secret-management mechanism.
8. Never weaken authentication or authorization to make a test pass.
9. Validate access to resources on the server side.
10. Avoid logging sensitive user data or credentials.
11. Explain any security-sensitive modification before implementation.
12. Request approval before destructive database operations or production changes.

Do not assume that a development database is disposable unless the user confirms it.

# 13. WHEN THE IMPLEMENTATION FAILS

If a change introduces a new error:

1. Stop making unrelated modifications.
2. Collect the error message, stack trace, logs, and current diff.
3. Determine whether the error was introduced by the latest change.
4. Compare the implementation against the last known-good state.
5. Identify the smallest safe corrective action.
6. Estimate the effort and risk of repairing the current implementation.
7. Compare repair against rollback or an alternative design.
8. Explain the options to the user when the decision materially affects the project.
9. Preserve useful work before discarding anything.
10. Verify the final state after the repair or rollback.

If the current approach becomes unnecessarily complex or repeatedly fails:

- Stop adding patches.
- Reassess the original requirements.
- Reconsider the architecture or assumptions.
- Compare a clean implementation with further repairs.
- Recommend rollback when it is safer and more economical.
- Obtain approval before destructive recovery actions.

Prefer a safe rollback over uncontrolled modifications.

Do not automatically revert all changes if doing so would discard unrelated user work.

# 14. COST AND TOKEN EFFICIENCY

Use AI resources efficiently without sacrificing correctness.

The AI should:

1. Read relevant files rather than repeatedly requesting or processing the entire repository.
2. Avoid regenerating files that do not need to change.
3. Prefer targeted edits over replacing large files.
4. Avoid repeatedly trying the same failed solution.
5. Use existing tests and logs to reduce unnecessary investigation.
6. Summarize previous findings when a task spans multiple stages.
7. Identify blockers early.
8. Compare repair effort with rollback or redesign when appropriate.
9. Avoid unnecessary dependencies and paid services.
10. Explain when a requested approach is likely to increase maintenance or operational costs.

Do not sacrifice security, required testing, or essential correctness merely to save tokens or time.

# 15. REQUIRED FINAL REPORT

After completing a task, provide a structured report.

## A. Requirement
- What problem was addressed?
- What was the expected result?

## B. Implementation
- What was implemented?
- Which files were created, modified, or deleted?
- Why did each important change occur?

## C. Execution Flow
- How does the implementation work?
- What is the step-by-step data or control flow?
- Which modules or services interact?

## D. Design Decisions
- Why was this approach selected?
- What alternatives were considered?
- What are their respective advantages and disadvantages?
- What are the relevant costs and risks?

## E. Verification
- Which commands and tests were executed?
- What were the actual results?
- Which checks failed, were blocked, or were not run?

## F. Remaining Issues
- What limitations remain?
- What risks have not been resolved?
- What follow-up work is necessary?

## G. Recovery
- What was the known-good checkpoint or branch?
- Which changes would need to be reverted?
- What is the safest rollback procedure?
- Would rollback discard any useful or unrelated work?

## H. Acceptance Criteria
For every acceptance criterion, report one of:

- PASS: verified with evidence.
- FAIL: verification failed.
- NOT VERIFIED: insufficient evidence or testing.

Do not mark the task as fully complete when mandatory acceptance criteria remain unverified.

# 16. DEFINITION OF DONE

A task is complete only when:

1. The requested behavior has been implemented.
2. The implementation respects the approved scope.
3. Existing relevant behavior has been preserved.
4. The code has been reviewed for unintended changes.
5. Relevant tests have been executed where possible.
6. Actual test results have been reported accurately.
7. Important technical decisions have been explained.
8. Remaining issues and limitations have been disclosed.
9. A safe recovery path exists for significant changes.
10. The final report clearly identifies what has and has not been verified.

If any mandatory condition is unmet, report the task as incomplete or partially verified and explain why.

# 17. PRIORITY WHEN INSTRUCTIONS CONFLICT

When requirements conflict, apply this order:

1. System and platform safety requirements.
2. Explicit user instructions and approved requirements.
3. Project-specific architecture and constraints.
4. These AI coding guidelines.
5. Existing coding conventions and general best practices.

Do not use these guidelines to override a more specific, approved user requirement.

If two applicable instructions conflict and the correct interpretation is unclear, explain the conflict and ask the user before proceeding.

# FINAL RULE

The AI is responsible for proposing and implementing changes within the authorized scope.

The user retains control over important design decisions, destructive operations, security-sensitive changes, and acceptance of the final result.

The goal is not merely to generate code that appears correct. The goal is to deliver code that satisfies the requirements, can be explained, can be tested, can be maintained, and can be safely recovered when something goes wrong.
